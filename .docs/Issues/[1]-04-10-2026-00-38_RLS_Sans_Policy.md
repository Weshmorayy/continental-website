# Issue : RLS activée sans policy effective

## Détails
- **Date** : 05-10-2026-00-38
- **Statut** : Résolue

## Description

Un visiteur anonyme pouvait lire les sauvegardes du site et la médiathèque.
Aucune erreur, aucun avertissement : les données étaient simplement servies,
à l'identique d'un contenu public. Les policies existaient, écrites
correctement, et n'étaient jamais évaluées.

## Cause Racine

Supabase n'applique une policy que si la RLS est *activée* sur la table.
`media` et `site_backups` disposaient de policies valides, mais
`pg_class.relrowsecurity` valait `false` : PostgREST ignorait ces policies et
servait toutes les lignes. Une policy inerte est indiscernable d'une policy
active lorsqu'on relit le SQL.

`FORCE ROW LEVEL SECURITY` n'a délibérément pas été exigé : le propriétaire
des tables est `postgres`, qui est aussi le rôle sous lequel les migrations
s'exécutent. L'exiger soumettrait les migrations elles-mêmes au filtrage par
policies, et les ferait échouer.

## Solution

La migration `supabase/008_fix_rls.sql` active la RLS sur les deux tables.
Elle installe aussi un garde-fou de non-régression qui lève une exception
dès qu'une table du schéma `public` se retrouve avec un
`relrowsecurity = false`. Les 15 tables publiques ont désormais la RLS active.

## Prévention

Après chaque migration, vérifier par une requête sur `pg_class` et non en
relisant le SQL. Un fichier de policies ne prouve jamais que les policies
sont appliquées — il prouve seulement qu'elles ont été tapées.

```sql
SELECT relname
FROM pg_class
WHERE relnamespace = 'public'::regnamespace
  AND relkind = 'r'
  AND NOT relrowsecurity;
```

Zéro ligne renvoyée = la RLS est active sur toutes les tables publiques. Le
garde-fou de `008_fix_rls.sql` fait de cette requête une vérification
obligatoire à chaque déploiement plutôt qu'un contrôle manuel.
